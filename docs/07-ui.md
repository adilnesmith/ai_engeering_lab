## `gr.Blocks` vs `ChatInterface`

Gradio has two ways to build a chat UI:

| `ChatInterface` | `gr.Blocks` |
|----------------|-------------|
| One-liner setup | Manual layout with full control |
| Chat only | Can add any component (panels, buttons, state) |
| Can't add a sidebar | Can have columns, tabs, accordions |
| Good for demos | Good for real apps |

Jarvis uses `gr.Blocks` because we need the task and note panels alongside the chat. Think of `gr.Blocks` as JSX — you compose components in a `with` block.

```python
with gr.Blocks(theme=gr.themes.Soft()) as demo:
    with gr.Row():
        with gr.Column(scale=3):    # 3/4 width — chat area
            chatbot = gr.Chatbot(...)
            msg_input = gr.Textbox(...)
        with gr.Column(scale=1):    # 1/4 width — sidebar
            tasks_panel = gr.JSON(...)
            notes_panel = gr.JSON(...)
```

`scale=3` and `scale=1` work like CSS `flex: 3` and `flex: 1`.

## Streaming Responses

Streaming means tokens appear one by one as the LLM generates them — instead of waiting for the complete response.

### The `yield` Pattern

```python
async def stream_response(message, history, thread_id):
    # Add user message to history
    history = history + [{"role": "user", "content": message}]
    history = history + [{"role": "assistant", "content": ""}]   # placeholder
    yield history, "", tasks, notes    # immediately show user message in UI

    partial_response = ""

    async for event in supervisor_graph.astream_events(..., version="v2"):
        if event["event"] == "on_chat_model_stream":
            chunk = event["data"]["chunk"]
            partial_response += chunk.content
            history[-1]["content"] = partial_response   # update placeholder
            yield history, "", tasks, notes              # push token to browser
```

An `async def` that uses `yield` is an **async generator** — each `yield` pushes an update to the browser. Gradio listens for these updates and re-renders the chatbot component.

In JS, this is equivalent to:
```javascript
async function* streamResponse(message, history) {
  for await (const token of llm.stream(message)) {
    yield { ...history, lastMessage: history.lastMessage + token };
  }
}
// Gradio's Python equivalent of ReadableStream
```

### `astream_events` — What Events Are Available

```python
async for event in graph.astream_events(input, config, version="v2"):
    event_type = event["event"]
    # "on_chat_model_stream"  → individual LLM tokens
    # "on_tool_start"         → a tool is about to be called
    # "on_tool_end"           → a tool finished and returned a result
    # "on_chain_start"        → a chain/node started
    # "on_chain_end"          → a chain/node finished
```

`version="v2"` is required — v1 is deprecated in LangGraph >= 0.2.

### Tool Usage Indicators

When the agent calls a tool, a `🔧 \`tool_name\`` indicator appears in the chat before the response. This shows the user what actions the agent took:

```python
elif event_type == "on_tool_start":
    tool_name = event.get("name", "tool")
    indicator = f"🔧 `{tool_name}`"
    tool_indicators.append(indicator)
    history[-1]["content"] = "\n".join(tool_indicators) + "\n\n_Thinking..._"
    yield history, "", tasks, notes
```

This gives real transparency into what the agent is doing — useful for demos and for understanding agent behaviour.

## `gr.State` — Session Management

```python
thread_id_state = gr.State(value=f"session-{uuid.uuid4().hex[:8]}")
```

`gr.State` stores a value per browser session. Every visitor gets their own `thread_id` — their conversations are isolated from each other.

Compare to React:
```javascript
const [threadId, setThreadId] = useState(`session-${crypto.randomUUID().slice(0, 8)}`);
```

The difference: Gradio state lives on the **server**, React state lives in the **browser**. Each user's state is maintained by the Gradio server process.

When "New Conversation" is clicked:
```python
def new_conversation():
    new_thread = f"session-{uuid.uuid4().hex[:8]}"   # new session ID
    return [], new_thread, tasks, notes
    # clears chat history, generates new thread_id (new LangGraph session)
    # does NOT delete notes or tasks — data always persists
```

## Live Sidebar Panels

The `tasks_panel` and `notes_panel` use `gr.JSON` to display structured data. They query the database directly (no agent needed) and refresh after every chat exchange.

```python
def get_sidebar_data():
    raw_tasks = db.list_tasks(status="pending")
    tasks = [{"title": t["title"], "due": t["due_date"], "id": t["id"][:8]} for t in raw_tasks]
    raw_notes = db.list_notes(limit=5)
    notes = [{"title": n["title"], "tags": ..., "created": n["created_at"][:10]} for n in raw_notes]
    return tasks, notes
```

The sidebar loads on page open via `demo.load(fn=refresh_panels, ...)` and updates after every message response.

## Error Handling

The UI handles two main failure modes gracefully:

**Ollama not running:**
```python
if not is_ollama_running():
    history[-1]["content"] = "⚠️ Ollama is not running. Start it with:\n```\nollama serve\n```"
    yield history, "", tasks, notes
    return
```

**Graph import failure** (e.g. missing dependencies):
```python
try:
    from agents.supervisor import supervisor_graph
    GRAPH_AVAILABLE = True
except Exception as e:
    GRAPH_AVAILABLE = False
    _IMPORT_ERROR_MSG = str(e)
```

Both cases show friendly messages in the chat instead of crashing. The UI always stays open and usable for diagnostic purposes.

## Wiring Events

Gradio events connect UI actions to Python functions:

```python
# Send button click → calls stream_response
send_btn.click(
    fn=stream_response,
    inputs=[msg_input, chatbot, thread_id_state],    # what to pass in
    outputs=[chatbot, msg_input, tasks_panel, notes_panel],  # what to update
)

# Pressing Enter in the textbox does the same
msg_input.submit(fn=stream_response, inputs=..., outputs=...)

# New conversation button
clear_btn.click(fn=new_conversation, inputs=[], outputs=[chatbot, thread_id_state, ...])

# Page load — populate sidebar immediately
demo.load(fn=refresh_panels, inputs=[], outputs=[tasks_panel, notes_panel])
```

This is like `addEventListener` in JS — except Gradio handles the HTTP transport automatically.
